# Architectural Decisions — Burak → Venturo Migration

Every decision below was made explicitly during this repo's audit/migration/ER-modeling sessions (see [VENTURO_AUDIT.md](../VENTURO_AUDIT.md), [VENTURO_ER_MODEL.md](../VENTURO_ER_MODEL.md), [AGENTS.md](../AGENTS.md)), not inferred after the fact.

| # | Decision | Why | Risks | Alternatives considered |
|---|---|---|---|---|
| 1 | Keep the system **single-tenant** (exactly one `ADMIN`-type member per deployment, enforced by `MemberService.processSignup` rejecting a second signup). | This was already the pre-existing behavior; the migration's job was to fix naming/domain, not redesign the tenancy model. `AGENTS.md` codifies it as a standing rule: *"Single-tenant by design — don't 'fix' that assumption without asking first."* | If Venturo ever needs multiple stores (marketplace model), this becomes a real rewrite of `Member`, `Product` ownership, and most admin-panel queries — not a small patch. | Making it multi-tenant now (adding a store/owner reference to `Product`) was considered and explicitly rejected as out of scope — it's a business-model decision, not a naming one. |
| 2 | **Don't bump major dependency versions** (Mongoose 6, Express 4, etc.) unless something is actually broken by the current version. | Migration risk should stay isolated to the naming/domain change being made. Bundling a dependency major-version bump with a rename makes it impossible to tell which change caused a regression. Codified in `AGENTS.md`. | Repo stays on Mongoose 6.2.9 / Express 4.17 / mongodb driver 3.2.6, which will eventually need upgrading for security patches — deferred, not avoided. | Upgrading opportunistically "while we're in here" was rejected — that's how scope creep turns a rename into an unplanned framework migration. |
| 3 | **Leave internal "restaurant"-named code identifiers unchanged**: `restaurant.controller.ts`, the `restaurantController` object, `getRestaurant`/`verifyRestaurant` function names, the `/member/restaurant` route path, and CSS classes like `.restaurant-menu-frame`/`.dish-container`/`.new-dish-txt`. | The task scope was explicit: rename the `MemberType.RESTAURANT` **enum value** and update **user-visible label text/EJS views/form options** referencing the old domain — not rename source files, function names, routes, or CSS selectors. Renaming those wasn't requested and increases blast radius (route path changes break any existing client; identifier renames touch more files for zero user-facing benefit). | Codebase now has an inconsistency: the enum says `ADMIN`, but the function that fetches that member is still called `getRestaurant()` and the route is still `/member/restaurant`. A future contributor unfamiliar with this history could be confused. | Renaming everything for full internal consistency was considered and rejected for this pass — flagged instead as a deliberate, documented scope boundary so it can be revisited intentionally rather than silently done alongside unrelated fixes. |
| 4 | **`ProductStatus.DELETE` remains soft-delete only** — no hard-delete endpoint was added. | This was already the pre-existing behavior (setting status to `DELETE` just excludes the product from `getProducts`'s `PROCESS`-only filter; nothing removes the document). Not part of any requested fix. | Deleted-status products accumulate in the database forever with no purge path. | Adding a real hard-delete endpoint was considered (it's a natural companion to the status enum) but rejected as a new feature outside what was asked — logged as an open question in `VENTURO_ER_MODEL.md` instead of decided unilaterally. |
| 5 | **Remove `ProductVolume` entirely** rather than generalize it into a reusable "variant"/"unit" concept. | Explicit instruction: outdoor gear doesn't have a drink-volume analog, and no requirement for a generic variant system was raised. Minimal, scoped change over a speculative abstraction. | If a future category needs its own secondary dimension (e.g., rope length, tent capacity), there's no reusable field for it — it would need to be designed from scratch. | A generic `productVariant: { label: string, value: string }` field was considered (it would have covered both the old drink-volume case and future cases) but rejected as premature — no current requirement justifies the added complexity ("don't design for hypothetical future requirements"). |
| 6 | **`ProductSize` made schema-optional** (removed the `default: "NORMAL"`) instead of keeping a forced default. | Not every new category (e.g. `CAMPING` gear) has a meaningful "size" the way `APPAREL`/`FOOTWEAR` do. Forcing every product to silently default to `"NORMAL"` would misrepresent products that were never sized at all. | Any existing query or UI that assumed `productSize` is always present will now need to handle `undefined`/`null`. | Keeping the default and just widening the enum's meaning was considered and rejected — a silent, incorrect default is worse than an explicit optional field. |
| 7 | **Scoped-pass-with-verification workflow**: each round of changes (bug fixes → dead-code removal → renames → wording sync) was applied as a discrete section, with `npx tsc --noEmit` run after every section before moving to the next. | Isolates failures to the section that caused them; matches `AGENTS.md`'s standing rule ("Run `npx tsc --noEmit` after any change before considering it done") and the working note captured in `SKILLS.md` about verifying after every edit round. | None significant — this is a process decision, not a code-shape one. Slightly slower than one big pass, in exchange for much easier failure attribution. | A single combined pass with one typecheck at the end was considered and rejected — harder to isolate which change broke the build if something failed. |
| 8 | When renaming an enum value, **grep for both the enum reference and the bare string literal** of the old value (not just `MemberType.RESTAURANT`, but also `"RESTAURANT"` as a raw string in EJS/JS). | Some code compares against raw string literals instead of the enum symbol (e.g. `src/views/signup.ejs`'s hidden `<input value="RESTAURANT">`, `src/public/js/products.js`'s `selectedValue === "DRINK"` check). A TypeScript-only search would miss these and leave the frontend/admin forms sending stale values that fail the new schema's `enum` validator. Captured as a standing working note in `SKILLS.md`. | Low — this is a search-thoroughness practice, not a code risk. | Relying on TypeScript compiler errors alone to catch every reference was considered and rejected — EJS/JS string literals are invisible to `tsc`. |
| 9 | **Wishlist proposed as a new, separate join collection** (`{ memberId, productId, createdAt }`) rather than an embedded array of product IDs on `Member`. | `View` (the closest existing analog) is insert-only with no delete path, because it models permanent view-count history, not a togglable "saved" state. A wishlist needs add *and* remove. A separate collection also naturally supports per-item "date added," pagination, and doesn't bloat the `Member` document. | None yet — this is a proposal, not implemented. If wishlists stay small (a handful of items per customer), the embedded-array alternative would have been simpler. | Embedding `wishlistProductIds: ObjectId[]` directly on `Member` was considered and is explicitly still open for revisiting — logged as Open Question #7 in `VENTURO_ER_MODEL.md` rather than settled. |
| 10 | **Order Track proposed as additive fields on the existing `Order` schema** (address snapshot, optional `trackingNumber`/`statusHistory`) rather than a new entity. | `Order` already carries `orderStatus` and timestamps and is already joined with `OrderItem`/`Product` in `getMyOrders`. The gaps (no address snapshot, no per-stage timeline) are missing *fields*, not a missing *relationship* — doesn't warrant a new collection. | If a full multi-stage timeline with carrier webhooks is eventually needed, an embedded `statusHistory` array may not scale as cleanly as a dedicated `OrderEvent` collection. | A separate `OrderTracking`/`OrderEvent` entity was considered and rejected for now as more structure than the currently-known requirements justify — revisit if Open Question #5 (status granularity) demands it. |
| 11 | **FAQ and Contact Us explicitly left as open product decisions**, not resolved by assuming either a static or DB-backed design. | Nothing in the repository indicates whether FAQ needs non-engineer editability or whether Contact Us submissions need an admin-reviewable inbox — deciding either way would be inventing a requirement, not documenting one. | None from *not* deciding — the risk runs the other way: guessing wrong would mean building the wrong entity (or over-building one that isn't needed). | Defaulting both to "static, no schema" (the simplest option) was considered but rejected in favor of surfacing the decision explicitly, since a wrong default could block a real requirement without anyone noticing until later. |
| 12 | **`SESSION_SECRET` wired from the existing `.env` variable** into `express-session`'s `secret` option, replacing a hardcoded literal string, rather than introducing new configuration. | The env var already existed in `.env` and was simply never read anywhere in the code — this is closing an existing gap, not adding new config surface. | Deploys that don't set `SESSION_SECRET` will now fail differently (an `undefined` secret is cast `as string`) rather than silently using the old hardcoded value — acceptable since the old behavior (hardcoded secret in source) was itself the actual security issue. | Leaving the hardcoded secret and just deleting the unused env var was considered and rejected — that would remove the *fix* to keep the *bug*. |
