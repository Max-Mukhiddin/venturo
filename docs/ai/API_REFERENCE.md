**One trap for a Postman collection specifically**: every enum above has identical key and value casing (`ADMIN = "ADMIN"`, `PENDING = "PENDING"`, etc.) — **except `ProductSortBy`**, whose values are `camelCase` field names (`"createdAt"`, `"productPrice"`, ...), not the `UPPER_SNAKE` key names. The `order` query param on `GET /product/all` must be sent as e.g. `order=productPrice`, not `order=PRODUCT_PRICE`. If a saved request sends the key-style string, it silently falls back to `createdAt` descending rather than erroring (see `ProductService.getProducts`'s whitelist-with-fallback logic) — worth checking explicitly since it fails silently, not loudly.

## 5. Runtime validation pass — all 32 endpoints, real requests

Every route in Section 3 (18 in `router.ts`, 14 in `router-admin.ts`) was hit with a real request against a running server and the dev database — not inferred from source reading alone. **32/32 passed.**

One real bug was found and fixed in the process: `GET /order/all` with no `orderStatus` query param returned `[]` instead of all the member's orders. `OrderService.getMyOrders` built its aggregation `$match` stage as `{ memberId, orderStatus: inquiry.orderStatus }` unconditionally — when `orderStatus` was omitted, that object still carried the key with a literal `undefined` value, and an aggregation `$match` stage (unlike Mongoose's `.find()`) does not strip `undefined` keys, so it matched on `orderStatus: undefined` and returned nothing. Fixed by building the match object conditionally: `orderStatus` is only added to the filter if `inquiry.orderStatus` is actually present, so an omitted filter now matches on `memberId` alone. Confirmed live: the same order that previously returned `[]` on an unfiltered request now returns correctly, and the matching-filter, non-matching-filter, and invalid-filter (400) cases were all re-checked afterward with no regression.

Every other route — including all 9 admin-session-gated routes (`/admin/product/all`, `/admin/product/:id`, `/admin/user/all`, `/admin/user/edit`, `/admin/article/all`, `/admin/article/create`, `/admin/article/:id`, `/admin/contact/all`, `/admin/contact/:id`) and the full `Article` create → publish → publicly-visible lifecycle, previously untested — passed as documented in Section 3.
